# `@canvas/web` — редактор цепочки нод

Рабочие пространства, канвас «текст → генератор → результат», сохранение графа через REST с
debounce и тестовая генерация изображения. React 19, TypeScript, Vite, React Flow
(`@xyflow/react`), CSS-модули, `motion` для переходов. Данные приходят только из API этого репозитория; типы берутся
из `packages/contracts`, поэтому схема запроса и тип ответа не расходятся.

Оформление держится на воздухе и типографике, а не на рамках. Шрифт — Onest, он ставится
пакетом `@fontsource-variable/onest` и попадает в сборку, поэтому при запуске нет обращений
к внешним сервисам.

## Запуск

Нужны Node.js 24.x и npm 11.x. Из свежего клона, из корня репозитория:

```sh
npm ci                 # зависимости всех рабочих пакетов
npm run dev            # терминал 1: API на http://localhost:4001
npm run dev:web        # терминал 2: фронтенд на http://localhost:5174
```

Сборка, предпросмотр и проверки:

```sh
npm run build:web                    # проверка типов и сборка в apps/web/dist
npm run test:web                     # модульные тесты (Vitest)
npm run e2e:web                      # сквозные сценарии (Playwright)
npm run preview -w @canvas/web       # предпросмотр собранной сборки
npm run typecheck -w @canvas/web     # только проверка типов
```

Перед первым запуском сквозных тестов один раз поставьте браузер:
`npm run e2e:install -w @canvas/web`. Playwright сам поднимет API и фронтенд; если они уже
запущены, он переиспользует их.

Адрес API по умолчанию — `http://localhost:4001`. Другой адрес задаётся переменной
`VITE_API_URL` (см. `.env.example`). Файл фиксации зависимостей — корневой
`package-lock.json`, он обновлён вместе с зависимостями фронтенда.

## Устройство работы с API

Запрос проходит четыре слоя, и каждый можно менять независимо.

| Слой              | Файл                    | Отвечает за                                                                                |
| ----------------- | ----------------------- | ------------------------------------------------------------------------------------------ |
| Описание запроса  | `src/api/endpoints.ts`  | Метод, путь, тело, условие `If-Match`, область ключа идемпотентности                       |
| Отправка и разбор | `src/api/transport.ts`  | Базовый адрес, общие заголовки, сериализация, статус, разбор тела, приведение ошибок       |
| Политики вызова   | `src/api/client.ts`     | Подстановка `If-Match` и `Idempotency-Key`, повтор безопасного запроса при обрыве связи    |
| Состояние         | `src/store/document.ts` | Черновик, debounce, очередь сохранений, версия, конфликт; `src/store/resource.ts` — чтения |

`fetch` вызывается ровно в одном месте — в `send()` из `src/api/transport.ts`. Там же один
раз проверяется статус, обрабатывается отсутствие тела у `204` и `304`, читается тело и
вынимаются заголовки `ETag`, `Location`, `Retry-After`, `X-Request-Id`. Компонент получает
`Result<T>` с типизированным `data` либо `AppError`; сырого `Response` он не видит.

Ошибки четырёх происхождений — обрыв связи, таймаут, отмена и ответ с телом ошибки —
сводятся к одному типу `AppError` с полями `kind`, `code`, `status`, `message`, `requestId` и
признаками `retryable`, `aborted`, `uncertain`. Последний отвечает на вопрос «мог ли запрос
дойти до сервера»: от него зависит, можно ли просто повторить запись.

Новый запрос добавляется одной записью в таблице `api`: остальное уже есть.

### Debounce и очередь сохранений

Вся логика сохранения живёт в `createDocument` (`src/store/document.ts`) — это общий
механизм, а граф лишь его настройка (`src/store/graph.ts`). Четыре правила описаны там один
раз:

1. **Одно сохранение на серию правок.** Таймер на 500 мс перезапускается на каждое изменение,
   поэтому набор текста или перетаскивание ноды дают один `PUT` после паузы.
2. **Сохранения одного графа идут строго по очереди.** Пока запрос выполняется, новые правки
   только помечают документ изменённым; следующее сохранение начнётся после ответа и возьмёт
   из него свежий `ETag`.
3. **Ответ не затирает более новые правки.** Из ответа берётся только версия, значение
   остаётся тем, что на экране: ответ прошлого запроса по определению старше локального
   состояния.
4. **Конфликт не теряет работу.** При `412` черновик остаётся, автосохранение
   останавливается, а решение перечитать серверный граф принимает пользователь.

`flush()` снимает таймер и дожидается очереди. Кнопка генерации вызывает его первой, поэтому
учитывает и не сработавший debounce, и уже отправленный запрос. Если сохранение не удалось,
генерация не запускается — иначе сервер считал бы снимок другого графа.

Отдельно разобран потерянный ответ `PUT`: при обрыве связи запрос мог успеть записаться.
Повтор с прежним `ETag` дал бы `412`, поэтому версия перечитывается. Изменилась — запись
прошла, и локальное состояние (оно новее) уходит поверх с актуальной версией. Не изменилась —
записи не было, и ошибка возвращается как обычная сетевая для повтора.

### Что ещё вынесено в одну реализацию

- **Показ ошибки.** `ErrorAlert` принимает `AppError` или его отсутствие и сам решает, показываться ли. Условие `error !== null ? … : null` исчезло из всех мест вызова: на экране канваса его было семь.
- **Приведение ошибки.** `toAppError` и `swallowAppError` живут в `src/api/errors.ts`; раньше первая была скопирована в трёх модулях состояния, а вторая — в двух.
- **Элементы управления.** Поле текста ноды и выпадающий список сценария берут рамку, фон и состояние фокуса из общего класса `control`: три копии одного правила фокуса свелись к одной.
- **Тона.** Индикатор сохранения и сообщения используют один набор классов `toneSuccess`, `toneError`, `toneWarning`, `toneInfo`.
- **Подпись ошибки поля.** `FieldError` — одна разметка и одна связь через `aria-describedby`.

Повторы проверяются не на глаз: одинаковые тела функций, куски разметки и наборы CSS-свойств
ищутся сравнением по нормализованному тексту. На момент сдачи совпадений нет.

### Распределение обязанностей

- `src/api` — транспорт, описания запросов, ошибки, ключи идемпотентности, опрос.
- `src/store` — внешнее состояние: документ с отложенным сохранением, ресурсы чтения, реестр графов по пространствам.
- `src/hooks` — связь состояния с React: `useResource`, `useAction`, `useStoreValue`.
- `src/lib` — чистые функции: работа с коллекциями, стабильное представление тела запроса, прерываемая пауза, хранилище браузера.
- `src/ui` — общий интерфейс: кнопка с ожиданием, поле с подписью и ошибкой, состояния загрузки и ошибки, общие параметры движения.
- `src/features/canvas` — типы канваса, правила связей, проекция в граф API, ноды.
- `src/features/generation` — запуск, опрос и запись результата.
- `src/pages` — список пространств и экран канваса.

Повторяющееся поведение живёт в одном месте: ожидание и блокировка любой кнопки — в
`useAction`; загрузка, ошибка и повтор любого чтения — в `useResource` и `AsyncView`;
ожидание результата — в `poll`; правила связей и готовности цепочки — в `rules.ts`.

## Разбор участка обработки графа

Самая частая обработка — проекция канваса в граф API (`projectGraph` в
`src/features/canvas/model.ts`).

**Частота.** React Flow сообщает об изменениях на каждое движение указателя при
перетаскивании ноды и при панорамировании — порядка 60 раз в секунду. Кроме того, после
монтирования приходит пачка служебных изменений `measured`, а выделение ноды меняет
`selected`. После каждого изменения нужно понять, изменилась ли сохраняемая часть графа.

Прямолинейный вариант — собрать граф заново:

```ts
const graph = {
  nodes: nodes.map((node) => ({
    id: node.id,
    type: node.type,
    position: node.position,
    data: node.data,
  })),
  edges: edges.map((edge) => ({ id: edge.id, source: edge.source, target: edge.target })),
  viewport,
};
```

Это новый объект на каждое движение указателя. Документ считал бы правкой даже появление
`measured`, перезапускал таймер и отправлял бы `PUT` там, где граф не менялся.

**Проходы.** Реализация делает один проход по нодам и один по связям, обращаясь к прежним
объектам по `Map` вместо поиска внутри обхода. Неизменившиеся ноды и связи возвращаются
прежними ссылками, а если не изменилось ничего — возвращается прежний граф целиком. Тогда
`document.edit` видит ту же ссылку и не планирует ничего.

**Память.** Две `Map` по прежнему графу и не больше двух новых массивов. При перемещении
одной ноды создаётся один новый объект ноды; массив связей и объект viewport остаются
прежними. Накопление идёт через `push` в изначально пустой массив: он остаётся плотным, без
дырок, которые появились бы у `new Array(n)` и перевели бы массив в `HOLEY_ELEMENTS`.

Тот же приём работает и в обратную сторону: `memo` на нодах вместе с точечной заменой одной
ноды (`replacePrompt`) оставляет перерисовку той ноды, которую действительно поменяли.

Второй частый участок — проверка допустимости связи. Она вызывается на каждое движение
указателя, пока пользователь тянет связь. Вместо поиска по массивам нод и связей строится
`GraphIndex` (`src/features/canvas/rules.ts`): один проход по нодам и один по связям дают
тип ноды по идентификатору, занятые входы и результат каждого генератора. Дальше любая
проверка — обращение по ключу, а индекс пересобирается только при изменении графа.

## Устойчивость

- **Двойное нажатие.** `useAction` не запускает второе действие, пока не завершилось первое. Второй барьер — `Idempotency-Key`: пока нода, версия графа и сценарий те же, ключ прежний, и повтор после потери ответа возвращает ту же генерацию.
- **Новый запуск против повтора.** Ключ привязан к отпечатку `[nodeId, graphETag, scenario]`. Поэтому повтор после отказа получает новый ключ автоматически: текст или версия графа к этому моменту уже другие, а смена сценария меняет отпечаток напрямую.
- **Уже идущая генерация.** `409 GENERATION_IN_PROGRESS` не создаёт вторую попытку: список генераций перечитывается, активная находится и отслеживается дальше.
- **Отказ генерации.** `failed` приходит состоянием в успешном HTTP-ответе. Он показывается в генераторе и в ноде результата, кнопка меняется на «Повторить генерацию».
- **Остановка опроса.** Опрос идёт последовательно и прерывается по `AbortSignal` при уходе со страницы и закрытии пространства. Обогнать сам себя он не может, а на одну генерацию приходится одно наблюдение.
- **Чужой результат.** Ноды получают результат через индекс «нода результата → самая свежая генерация», построенный по списку от новых к старым. Поэтому старая попытка не может перекрыть новую, а результат удалённой цепочки некуда подставить.
- **Перезагрузка.** Граф и список генераций читаются заново, незавершённые генерации продолжают отслеживаться. Последнее открытое пространство запоминается, и приложение возвращает в него.
- **Целостность графа.** Удаление ноды уносит её связи, иначе сервер отклонил бы граф со связью на несуществующую ноду. Ограничения в 20 нод и 20 связей проверяются до запроса.

## Интерфейс

Панель сверху показывает состояние сохранения: «Есть несохранённые правки», «Сохраняем…»,
«Все правки сохранены», «Версии разошлись», «Не удалось сохранить». Отдельно показывается
случай «сохраняем, есть новые правки» — запрос идёт, но это уже не последнее состояние.

Ноды подписаны, порты видны, поле текста не перетаскивает ноду (`nodrag`), колесо внутри
поля не масштабирует канвас (`nowheel`). Генератор объясняет, чего не хватает для запуска,
до обращения к серверу. Отказ в связи объясняется словами: React Flow не создаёт
недопустимую связь сам, поэтому причина разбирается в `onConnectEnd`. Проверено на ширине
1280 пикселей; мобильная версия канваса заданием не требуется.

Все цвета, отступы, радиусы и типографика заданы токенами в `src/styles/global.css`, а
длительности и кривые переходов — в `src/ui/motion.tsx`: общее правило правится в одном
месте. Движение короткое и служебное: появление нод и сообщений, проявление результата,
смена цвета индикатора сохранения. Системная настройка «меньше движения» учитывается
централизованно.

Палитра проверена расчётом контраста: основной и приглушённый текст дают не меньше 4.5:1 на
всех поверхностях, где используются, а граница поля ввода — не меньше 3:1 к поверхности, как
требует правило для нетекстовых элементов. Тёмная тема проверена теми же парами.

Текст индикатора сохранения намеренно не анимируется подменой элемента: он должен меняться
сразу, иначе показывал бы устаревшее состояние. Плавность там даёт переход цвета.

## Проверенные сценарии

Модульные тесты (`npm run test:web`, 41 проверка) покрывают общий слой: сборку запроса и
заголовков, разбор тела, отсутствие тела у `304`, `ETag`, `Retry-After` и `Location`,
приведение сетевых, HTTP- и разборных ошибок к одному виду, правила ключей идемпотентности,
опрос до конечного статуса и его отмену, правила связей и готовности цепочки, проекцию
канваса в граф, работу с коллекциями и — отдельным набором — поведение документа: одно
сохранение на серию правок, очередь при медленном ответе, запрет подмены свежих правок
старым ответом, `flush`, конфликт версий, сетевую ошибку и повтор.

Сквозные сценарии (`npm run e2e:web`, 11 проверок) идут на живом API без подмены ответов:

1. Основной сценарий: пространство, три ноды, текст, связи, сохранение, генерация, изображение в ноде результата. Проверяется, что в запрос не попали служебные поля React Flow.
2. Серия быстрых правок даёт один `PUT`; одиночная правка тоже сохраняется.
3. Запуск сразу после правки: сначала уходит `PUT` графа, затем `POST` генерации, и сервер получает последний текст.
4. Несовместимая связь и второй вход не создаются, причина объясняется.
5. Удаление ноды уносит связи, сервер принимает оставшийся граф.
6. Конфликт версий: черновик остаётся, генерация не запускается, перечитывание возвращает серверный граф, работа продолжается.
7. Тестовый отказ показывается и допускает новый запуск; на сервере оказываются ровно две генерации.
8. Двойное нажатие создаёт одну генерацию.
9. Перезагрузка во время генерации: граф и текст восстановлены, незавершённая генерация дочитывается, результат переживает ещё одну перезагрузку.
10. Результат удалённой цепочки не подставляется в новую ноду результата.
11. Сбой сети при сохранении не теряет правки; повтор доводит их до сервера.

## Известные недоработки

- Слияние двух версий графа при конфликте не делается: пользователь выбирает между своим черновиком и серверным графом целиком. Заданием сложное слияние не требуется.
- Отмены действий (undo/redo) нет — она вынесена из задания.
- Условные чтения графа (`If-None-Match`, `304`) транспорт поддерживает, но приложение их не использует: граф перечитывается целиком.
- Ограничения графа берутся из `GET /api/config`, но пауза debounce остаётся константой 500 мс: она нужна при создании документа, до первого ответа сервера.
- Сценарий генерации выбирается общим переключателем в панели, а не у каждого генератора: это тестовый переключатель, а не часть графа, и в схеме API его нет.
- Нет автоматических тестов на компоненты в отрыве от браузера: поведение интерфейса проверяется сквозными сценариями.
- Список пространств не разбит на страницы и не имеет удаления: заданием это не предусмотрено.
- Мобильная раскладка канваса не прорабатывалась — по условию она не оценивается.
